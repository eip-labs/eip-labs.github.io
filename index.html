</> ARCHITECTURAL INTEGRITY

AI Software Architecting

How EIP-Labs designs AI-native systems software by keeping unpredictable AI output away from critical system control, and how every major technical choice is recorded and enforced with Architecture Decision Records.

LAYER 01 // SYSTEM BOUNDARY

Separating AI Guesswork From Deterministic Control

Standard web applications treat all code as equally trusted. AI systems cannot work that way. A language model produces probabilistic output — it is likely correct, but never guaranteed. Production infrastructure requires guaranteed behavior: the same input must always produce the same safe result. EIP-Labs enforces this with a hard architectural boundary. AI models propose; deterministic code disposes. Every model output is validated, bounded, and authorized by conventional software before it can touch state, memory, or hardware.

01
Decoupled Inference

Model responses (tokens) never write directly to application state. They pass through a fixed validation gate that only accepts well-formed, authorized commands. Creative AI output and system mutations live on opposite sides of that gate.

02
Failure Domain Isolation

A wrong or hallucinated model answer is treated as a contained fault. It is rejected at the boundary and cannot crash the host process, corrupt memory, or take down the operating system. Bad AI output fails closed, not open.

03
Monotonic State Clocks

Every state change carries a strictly increasing epoch number. Out-of-order or duplicated updates from a delayed replica are discarded. This prevents two nodes from simultaneously believing they own the truth (split-brain divergence).

04
Hardware Affinity

Core data structures are aligned to 64-byte CPU cache lines. This keeps neighboring threads from fighting over the same memory line (false sharing), preserving predictable low-latency execution under load.

LAYER 02 // DECISION GOVERNANCE

Architecture Decision Records (ADRs)

Complex systems degrade when nobody remembers why a design was chosen. An Architecture Decision Record is a short, permanent document that captures one important technical decision — the problem, the choice made, the options rejected, and the trade-offs accepted. At EIP-Labs, no structural change enters the codebase without an accepted ADR, and each ADR is linked to an automated compliance check so the decision is enforced by CI/CD, not by memory.

FIELD 01
Context

The concrete problem or constraint that forced a decision — stated once, with no solution bias.

FIELD 02
Decision

The single approach adopted, written as an active, testable statement the team is now bound to.

FIELD 03
Invariants Enforced

The non-negotiable properties the decision guarantees — measurable limits the runtime must never violate.

FIELD 04
Consequences

Honest gains and costs: what becomes simpler, and what becomes harder — both are recorded.

FIELD 05
Status

Proposed, Accepted, Deprecated, or Superseded — so readers always know if the decision still holds.

FIELD 06
Compliance Hook

A named automated check (unit gate or CI rule) that fails the build if the decision is ever violated.

Result: architectural intent survives team turnover, review is mechanical rather than opinion-based, and regressions against accepted decisions are caught before merge.

Test Strategy

Canonical Go pattern for executing multiple input/output scenarios through a single test runner. All unit tests must use table-driven patterns covering valid, invalid, boundary (zero, max, negative, overflow), and Unicode edge cases.

ENFORCEMENT: Only enabled when MUTATION_THRESHOLD > 0 in config.env. Default: disabled for tier-3, enabled for tier-1/2.

  • Execute mutation testing: go-mutesting ./...
  • Pass Threshold: Minimum kill rate from config.env (tier-1: 70%, tier-2: 50%, tier-3: 0/disabled).

3.3 Property-Based Testing

Generates randomized data matching strict schema invariants to discover edge-case input failures:

3.4 Fuzz Testing (Adversarial Inputs)

All public parsers, serializers, boundary decoders, and validation logic must have fuzz targets:

Authoring Invariants & Policies // Sections 09–11
09
Test Authoring Invariants
  • Deterministic Execution: Tests must not rely on wall-clock time (time.Sleep), random seeds without fixed initialization, or uncontrolled network state.
  • Hermetic Isolation: Each test must initialize and clean up its own resources. Tests must never depend on execution order.
  • Meaningful Assertions: Every test must assert specific error codes or message contents, not merely err != nil.
10
Mocking & Test Doubles Policy
  • Mock Interfaces (Ports), Never Concrete Implementations: Mocks or stubs are permitted only for boundaries defined in ports/ (e.g., database repositories, third-party payment gateways, message publishers).
  • No Mocking Internal Business Logic: Domain entities, value objects, and pure business calculations must be tested using real instances, not mocks.
  • Contract Verification: Mock behaviors must strictly adhere to the interface contracts documented in Phase 2.
11
Flaky Test Zero-Tolerance Policy

A test that passes and fails intermittently without code modifications is classified as a Flaky Test. Flaky tests represent a breakdown of determinism and must never be ignored or re-run until they pass.

Action: If a test flakes, the agent must identify the root cause (unbounded concurrency, race conditions, global state, or time reliance) and eliminate it.
